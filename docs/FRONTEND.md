# Intelligence dashboard (Milestone 9)

React 19 + Vite 8 + TypeScript 5.9 (strict), in `frontend/`. It is a **presentation layer only** over the Milestone 8 API (`/api/v1`):
- It re-implements no backend logic: no risk formula, thresholds, evidence-status rule, correlation, or approval policy.
- It can execute nothing.

```bash
cd frontend
npm ci                             # exact versions from package-lock.json
cp .env.example .env.local        # optional: VITE_API_BASE_URL (default http://127.0.0.1:8000)
npm run dev                        # http://localhost:5173 (the API's default CORS origin)
npm run check                      # typecheck + lint + tests with coverage + production build
```

Start the API first: `uvicorn hqc.api.server:create_api_app --factory --host 127.0.0.1 --port 8000` (see `API.md`).

## Architecture
```
src/
  api/        openapi.json (exported from the live API), schema.d.ts (generated), types.ts (aliases),
              client.ts (the ONLY networking module), validate.ts (runtime boundary checks),
              endpoints.ts (typed endpoint functions), apiContext/context/useApi (dependency injection)
  hooks/      useAsync (loading / error / ready, stale-response safe, keyed refetch)
  lib/        format.ts (display formatting, ATT&CK links), recent.ts (recent assessments + decisions)
  components/ ui (panels, states, badges, safety notices), AttackChainTimeline, PredictionPanel,
              RiskPanel, QuantumPanel, RecommendationsPanel, DecisionControls
  pages/      Overview, Assessments (list + submit), AssessmentDetail, Mitre, Evaluation, NotFound
  fixtures/   synthetic-assessment-request.json (generated by the backend's own M7 code)
  test/       harness (fetch mock + renderers), security scan, fixtures/ (REAL captured API responses)
```

**Contract-first types:**
- `scripts/export_frontend_contract.py` writes the API's exact OpenAPI document to `src/api/openapi.json`.
- `npm run gen:api` (openapi-typescript) generates `schema.d.ts` from it, so no API field is invented.
- A backend test (`tests/unit/test_frontend_contract.py`) fails if the committed contract drifts from the live API.
- `--responses` captures real API responses (in-memory API state) as test fixtures.

**State management:**
- Local component state plus the `useAsync` hook; no global store.
- The `Api` object is provided by React context, so tests inject one against a mocked `fetch`.
- After an analyst decision, the decision history is **re-read from the API**. The UI never edits it locally.

## Routes and API endpoints consumed
| Route | Page | Endpoints (GET unless noted) |
|---|---|---|
| `/` | Overview: API health, ATT&CK/vocabulary/model/policy versions, evaluation runs, recent assessments, risk-level distribution, recent analyst decisions | `/health`, `/api/v1/meta`, `/api/v1/runs`, `/api/v1/assessments`, `/api/v1/assessments/{id}`, `/api/v1/assessments/{id}/recommendations` |
| `/assessments` | Submit an `AssessmentRequest` (paste, upload, or load the SYNTHETIC example); stored assessments | **POST** `/api/v1/assessments`, `/api/v1/assessments` |
| `/assessments/:id` | Incidents: attack chain, predictions, risk, classical + quantum evidence, recommendations, analyst decisions | `/api/v1/assessments/{id}`, `…/recommendations`, **POST** `…/recommendations/{rid}/decisions` |
| `/mitre` | Techniques, tactics and mitigations seen in assessments; ATT&CK version | `/api/v1/meta`, assessments (as above) |
| `/evaluation` | Stored run summaries and metrics; current deployment versions | `/api/v1/runs`, `/api/v1/meta` |

**Not consumed:** the stateless `POST /chains/reconstruct`, `/predictions` and `/risk/assess` endpoints, and `GET /scenarios/synthetic`. Assessments already return the complete pipeline output.

**API gaps (handled in the dashboard, not by changing the frozen API):**
- **No technique-lookup endpoint.** The MITRE view shows only IDs the API returns: observed techniques with attributed tactics, predicted techniques, and mitigation IDs. IDs link to the public ATT&CK pages; that is navigation in a new tab, and nothing is fetched. Technique names and descriptions are therefore not shown, and the knowledge base is not recreated in the browser.
- **No global decision list.** Recent decisions are gathered from the recommendation views of recent assessments.
- **Run summaries carry no per-run model/policy versions**, because the API strips configuration. The current serving versions from `/meta` are shown instead and labelled as such.
- **Assessments need fully typed observations** (evidence statuses are computed by M7 backend code). The SYNTHETIC example request is generated by the backend's own `build_observations`; users can paste or upload their own JSON, which the API validates.

## Visual design system
`src/styles/theme.css` defines every colour, radius, spacing step and type size as CSS variables on `:root`. It uses system fonts only (no remote fetch) and adds no dependencies.
- **Palette:** near-black surfaces (`--bg #090B0B`, `--panel #121616`, borders `#282E2C`) with a single neon-lime accent (`--lime #A5FF78`) reserved for emphasis, links, focus rings and the primary action. Amber marks warnings and safety notices; a restrained red marks critical risk and rejection.
- **Contrast:** every text colour meets WCAG AA (≥ 4.5:1) on the page, panel and inset backgrounds. The faintest text is 4.9:1 on panels.
- **Type:** oversized editorial headings (`--fs-display`, tight tracking), muted secondary text and tabular numerals for scores.
- **Shape:** large rounded cards (28 px), thin low-contrast borders, subtle radial gradients and thin circular outlines (page hero, stat cards). Glow is limited to the lime dot, active nav item and primary-button hover.
- **Motion:** a short page fade-in, a slow orbit on the hero ornament, and hover/focus transitions. All motion is disabled under `prefers-reduced-motion`.
- **Observed vs predicted:** observed steps are solid with a filled lime marker. Predicted steps have a dashed violet outline, a hollow dashed marker and a hatched fill, sit below a dashed "forecast" boundary, and are labelled "Not observed, not confirmed".
- **Risk:** the API score sits inside a ring gauge (score/100, coloured by the API's level) next to the `MODEL-DERIVED RISK SCORE` disclaimer. Scores display with two decimals everywhere.
- **Decision controls:** three dashed "record" buttons with distinct colours and CSS-only glyphs: acknowledge (grey ring), approve (lime diamond) and reject (red square). None uses the solid primary style, so approval never looks like an action.
- **Responsive:** a top navigation that collapses behind a Menu toggle below 760 px (`aria-expanded`/`aria-controls`; it closes on navigation). Grids collapse at 1180/900/760 px. Wide tables scroll inside keyboard-focusable `region`s. Touch targets are ≥ 44 px on phones. No route scrolls horizontally at 390 px or 1440 px (checked in Chrome).

## Observed vs predicted visualisation
- **Observed steps:** solid nodes with a filled lime marker, labelled `OBSERVED #n`. Each shows the technique ID, attributed tactic, event timestamp, evidence confidence, evidence source and evidence text, in arrival order.
- **Predicted steps:** dashed violet nodes labelled `PREDICTED +n` with the text "Not observed, not confirmed — a model forecast". They show the top beam-search path.
  - The first predicted step shows its **next-step probability**.
  - The path shows its **PATH SCORE**, explicitly "not calibrated; not a probability of attack".
  - The API returns no tactic for predicted techniques, and the dashboard says so.
- **Prediction panel:** the primary model's next-step table, per-model top-k (B1, M1, LSTM, HYBRID), and beam paths. It reproduces the API's own semantics strings.

## Risk, quantum and recommendations
- **Risk panel:** shows the API's score, level, `MODEL-DERIVED RISK SCORE` label and every contributing factor (value, weight, points, reason), plus evidence status, uncertainty and affected assets. It never computes a score; tests check the displayed points equal the API's contributions.
- **Quantum panel:** per detection, the classical verdict (the decision) beside the quantum second opinion (verdict, probability, confidence, backend, latency when present), agreement or disagreement, and evidence status. It states that the quantum opinion **never overrides** the classical verdict and that no quantum advantage is claimed.
- **Recommendations:** each card shows:
  - the action as a *proposal* ("Consider isolating…"), target and rationale;
  - priority (urgency), confidence, disruption and reversibility;
  - ATT&CK mitigations and supporting evidence;
  - `PROPOSAL · PROPOSED`, `Human approval required: true`, `executed: false`;
  - the banner **"Recommendation only — no action has been executed."**

## Analyst approval workflow
The only controls are **Record acknowledgement**, **Record approval (does not execute)** and **Record rejection**. They are dashed "record" buttons, never action buttons, and each requires an analyst name.
- **HIGH-disruption proposals** explain the two-step rule (acknowledge, then approve). The rule is **enforced by the server**: the dashboard does not pre-empt it, and shows the server's 409 as "Workflow conflict (409): HIGH-disruption recommendations must be ACKNOWLEDGED before APPROVED".
- **After recording:** the API's decision record is shown with `executed: false`, and the history is re-read from the API.
- **The stored recommendation stays `PROPOSED`.**

## Security boundaries
**Network:**
- Only `api/client.ts` performs requests, to the base URL from `VITE_API_BASE_URL`, which is validated: http/https, no credentials, query or fragment.
- Requests use fixed path templates with URL-encoded IDs and `credentials: "omit"`.
- Requests to non-API paths are refused.

**Response handling:**
- Responses are checked at run time. A decision or view claiming `executed: true`, a recommendation without mandatory approval, a non-model-derived risk label, or mixed provenance is rejected as a contract error instead of being rendered.
- Errors are categorised (API unreachable, 503 missing artifacts, 422, 409, 404, contract, other) and sanitised: first line only, paths stripped, 422 bodies summarised without echoing input. Stack traces are never shown.

**Code and data:**
- No secrets, API keys or credentials in the source; there is no authentication yet.
- No `dangerouslySetInnerHTML`, `innerHTML`, `eval` or `new Function`. This is enforced by ESLint and by `src/test/security.test.ts`, which also checks that networking occurs only in the client and that no control or endpoint executes a recommendation.
- The frontend is never trusted for safety: approval rules, validation and the recommendation-only guarantee are enforced by the backend.

## Tests
**Vitest + Testing Library, 68 tests** (53 original, unchanged, plus 15 for the redesign: responsive navigation, submission lock, error recovery, overview headline, detail layout, decision-control styling, evaluation comparison and the display-only metric pivot):
- the API client (base URL, error mapping, sanitising, encoding, path refusal);
- boundary validation against real fixtures and tampered copies;
- the attack chain (observed vs predicted);
- the prediction, risk and quantum panels;
- recommendations (no execution controls);
- the decision workflow (name required, 409, acknowledge then approve, reject with note, other errors);
- pages (overview, 503 retry, API unavailable, empty states, assessment detail, decision refresh, 404, submission with local JSON error and server 422, MITRE and evaluation views, not-found page);
- the static security scan.

**Coverage:** 94% statements, 96% lines, 82% branches.

## Limitations
- There is no authentication: the analyst name is free text. Run locally only.
- Technique and tactic names are unavailable until the API exposes an ATT&CK lookup endpoint.
- The dashboard reads recent assessments with a few sequential requests (≤ 20 assessments on the MITRE view), with no pagination UI.
- The visual design was reviewed in headless Chrome at 1440 px and 390 px (screenshots and automated overflow checks); it has not been tested with assistive technology users.
